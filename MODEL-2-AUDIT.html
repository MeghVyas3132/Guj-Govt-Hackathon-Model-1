Why the Plates Don't Read

A measured audit of the Setu ML worker against the Sentinel sandbox. The camera quality is a real problem — but not the one it looks like, and not the one that is costing the most.

RepositoryGujarat-setu-ML @ 8e526ee
Reviewed4 Sep 2026
Submission closes7 Sep 2026
Scope2,249 lines · 19 files

The feeds are not low-resolution. Eighteen of the thirty sandbox cameras are 1920×1080 h264. What ruins them is bitrate: a measured 358 kbps, which is roughly 0.006 bits per pixel — about twenty times below what 1080p surveillance normally carries. The pixels are there; the detail was quantised away before it ever reached you.

That distinction decides what is worth doing. Nothing recovers detail the encoder discarded, so sharpening a single frame cannot work — and the pipeline's current CLAHE-and-unsharp chain actively amplifies the compression artefacts it is trying to see through. What does work is temporal: the same plate across thirty frames carries partly independent noise, so votes across frames recover glyphs no single frame holds.

The pipeline cannot do that today, because vehicle tracking is never switched on. That is the finding underneath the finding, and it is why this audit ranks a one-line bug above the camera quality everyone is looking at.

Findings, ranked by what they cost you

01

Vehicle tracking is never switched on

Critical

The README describes ByteTrack producing "consistent track_id across frames", and the pipeline reads box.id. But the call is model.predict(), and predict() never populates boxes.id — only model.track() does. There is no .track( anywhere in the repository.

ml/pipeline.py:44 results = self.yolo.predict(...) # not .track() ml/pipeline.py:62 track_id = int(box.id[0]) if box.id is not None else None -> box.id is always None -> track_id is always NULL

Everything downstream inherits this. There is no re-identification anchor, so "cross-camera vehicle tracking" has no thread to follow; the detections.track_id column is uniformly null; and — most expensively — multi-frame plate voting is impossible, which is precisely the technique that beats low-bitrate video.

FixSwitch to self.yolo.track(frame, persist=True, tracker="bytetrack.yaml"), then aggregate per track_id: collect every plate read for a track and take a per-character majority vote weighted by OCR confidence. Emit one consolidated vehicle record per track rather than one row per frame. This is the single highest-value change available.
02

Timestamps are ingestion wall-clock, not media time

Critical

process_frame() accepts pts_ms and never uses it. Every detection is stamped datetime.now() — the moment the worker happened to decode that frame, not the moment the vehicle passed. The schema comment claims otherwise.

ml/pipeline.py:41 def process_frame(self, frame_bgr, camera_id, pts_ms) # pts_ms unused ml/pipeline.py:56 ts = datetime.now(timezone.utc) scripts/schema.sql ts TIMESTAMPTZ -- "frame PTS (when detected, not when written)"

These are recorded 12-hour loops, and each camera thread walks its archive at a speed set by network luck. Two cameras processing concurrently stamp "now" regardless of where they are in their own timeline, so the interval between a vehicle at cam04 and the same vehicle at cam12 is pure scheduling noise. Route reconstruction and movement history — both explicitly scored deliverables — cannot be built on this.

FixDerive media time: archive_start + (segment_index × 6.0 s) + pts_ms. The segment index is already known in the fetch loop; thread it through and store it alongside. Keep the wall-clock separately as ingested_at if you want processing telemetry.
03

The preprocessing chain fights the compression instead of the noise

High

Plate crops are upscaled 3×, converted to grey, CLAHE-equalised, bilateral-filtered and unsharp-masked before OCR. At 0.006 bits per pixel the dominant signal in a plate crop is block and ringing artefact, and contrast equalisation plus sharpening amplifies exactly that. The chain is also unvalidated: compare_ocr.py benchmarks four OCR engines, but never A/Bs the preprocessing itself, even though run_fast_ocr() already takes a preprocess flag.

ml/pipeline.py:124-131 resize x3 -> COLOR_BGR2GRAY -> CLAHE(2.0) -> bilateral(9,75,75) -> GaussianBlur -> addWeighted(1.5, -0.5) # unsharp
FixRun the A/B you already have the switch for, on daylight segments, and let it decide. Add a hard gate first: skip any plate crop under roughly 60 px wide — below that there is nothing to read and every result is noise entering the database.
04

Plate correction can manufacture a plausible plate

High

correct_plate() tries six letter/digit segmentations, applies per-position character substitutions, then substitutes state-code characters until the prefix matches a real Indian state — and finally selects whichever candidate has the longest numeric group. A garbled read is therefore pushed toward something that looks valid rather than being rejected.

When validation fails entirely, the raw unvalidated string is returned anyway and written to the same plate_text column, so nothing downstream can distinguish a confident read from a salvage attempt from a guess. In a police context a fabricated-but-well-formed registration is materially worse than a null.

FixStore plate_raw, plate_corrected and a plate_status enum (exact / corrected / unvalidated) as separate columns. Alert and search on exact only; keep the rest for review. Record which substitutions fired, so a corrected plate can be defended when someone asks.
05

A global lock serialises every camera through one GPU call

Medium

The worker starts one thread per camera, but _inference_lock is a module-level RLock wrapping YOLO inference, so all thirty threads queue on a single critical section. Adding cameras adds latency, not throughput — and the README's "CAMERAS=all (GPU required)" will not behave as it implies.

ml/pipeline.py:19 _inference_lock = threading.RLock() ml/pipeline.py:43 with _inference_lock: # every camera thread waits here
FixBatch instead of serialise: have camera threads push frames onto a queue and run one inference thread that predicts on batches of 8–16. That uses the GPU properly and removes the lock. It also makes the scalability story you have to present far easier to defend.
06

Time-windowed playback prefetches the wrong segments

Medium

In _frames_hls() the loop iterates the sliced window but the prefetch thread indexes the unsliced segments list, and bounds-checks against its length. With start_time set, every frame after the first is decoded from the wrong point in the archive — silently, since both lists are valid segment URLs.

ml/stream.py:246 for seg_idx, seg_url in enumerate(window): ml/stream.py:255 if seg_idx + 1 < len(segments): # should be len(window) ml/stream.py:257 target=_prefetch, args=(segments[seg_idx + 1],) # should be window[...]
FixIndex window in both places. This matters now rather than later, because selecting the daylight window is the fix for finding 03.
07

Camera identity contradicts itself — unresolved

Verify

The sandbox catalogue names cam04 "04 Paldi Circle", and Model 1's registry maps it correctly. But the video served at /cam04/ carries a burned-in overlay reading Chiman bhai Bridge CSITMS-32_PTZ2 — which is the name of cam01.

I could not settle whether feeds are duplicated across IDs: the gateway throttled the comparison run to a single successful fetch. It needs settling before the demo. If two "different" cameras serve identical footage, a cross-camera tracking demonstration is showing the same vehicle to itself, and a judge who notices the overlay will see it too.

FixFetch the same segment index from all thirty cameras, hash the bytes, and count distinct content. Space the requests — the gateway throttles hard. Then choose demo camera pairs from confirmed-distinct feeds, and prefer pairs whose overlays agree with the catalogue.
08

The sandbox password is committed to a public repository

High

DBAD-4UQP-BSTV appears hardcoded in scripts/check_feeds.py and as a default in ml/config.py, and it is filled in as a live value in both committed env examples. .gitignore correctly excludes .env, which is what makes this easy to miss.

FixStrip the value from all four locations, leave the key with an empty placeholder, and tell the organisers it was exposed. Rewriting history is optional; disclosing is not.
09

Two env templates disagree with each other and with the code

Medium

.env.example and .env_example both exist and differ on three settings that change behaviour — including a plate-detector model and a confidence threshold that differs by a factor of two. Whoever sets up next gets a different pipeline depending on which file they copy.

.env.example .env_example PLATE_MODEL keremberke/yolov8n-... FarAwayFer/yolov8n_... (config.py agrees with this one) PLATE_CONF_THRESHOLD 0.5 0.25 DATABASE_URL localhost:5432 127.0.0.1:5433
FixDelete .env_example, reconcile the survivor against ml/config.py, and note in the README which plate detector the results were produced with.

What Model 1 already hands you

Some of the gap closes by wiring rather than building. Model 1 is running, migrated and seeded with all thirty cameras, and it already solves the sandbox's CORS, cookie and User-Agent constraints server-side. It exposes RS256 JWTs verifiable offline via JWKS, camera and stream lookup with reachability labels, an authenticated same-origin HLS relay, and signed webhooks on camera state.

Two cautions from measuring it today. The relay's manifest rewrite returns 1.06 MB and took 52–59 s for a single camera — usable for development, not for a video wall. And the AES key endpoint returned empty on two of three attempts before succeeding; to a player that presents as a decrypt failure. Both are Model 1's to fix, and both are worth fixing before either model is demonstrated.
